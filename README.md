# Nissan GT-R R35 Parts Catalog Prototype

This project now includes a local importer for your Nissan GT-R R35 workbook and a browser prototype for browsing the imported data.

1. Workbook data is imported from your Excel file.
2. Diagram images are extracted from the workbook into the project.
3. Parts, source links, and diagrams are written into app-ready data files.
4. The browser UI loads those generated files.

## Files

- `index.html`: Main app layout
- `styles.css`: Styling for the catalog UI
- `app.js`: UI logic for diagrams, part search, and the side panel
- `scripts/import-workbook.ps1`: Imports the Excel workbook into project data
- `data/catalog-data.json`: Generated catalog data
- `data/catalog-data.js`: Generated browser data bundle
- `assets/diagrams/`: Extracted diagram images from the workbook

## How to run

1. Run the importer:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\import-workbook.ps1
```

2. Open `index.html` in your browser.

The browser app reads `data/catalog-data.js`, which is generated by the import script.

## How to structure your real data

The importer currently maps your workbook into two main layers:

### 1. Parts table

Each part record should contain:

- `partNumber`
- `description`
- `supplierUrl`
- `group` or `partFamily`
- `similarParts`

Imported from the `Organized Parts` sheet and enriched with part links from `Sheet1`.

### 2. Diagram table

Each diagram record should contain:

- `id`
- `title`
- `image`
- `hotspots`

Imported from the `diagrams` sheet and paired with the workbook's embedded images.

Right now, the importer extracts the diagram images and source-page URLs, but it does not yet know the exact clickable position of each callout number on each image. Those hotspot coordinates still need to be mapped in a later step.

## Recommended production setup

For the full production system, the cleanest build path is:

1. Keep importing the Excel workbook into structured data.
2. Add a hotspot editor so each diagram callout can be mapped visually.
3. Store all parts, diagrams, and hotspot coordinates in a database.
4. Build the frontend so diagram clicks call a part lookup by part number.
5. Return the selected part plus all related alternatives from the database.

Suggested stack:

- Frontend: React or plain HTML/JavaScript
- Backend: Node.js with Express
- Database: SQLite for easy local setup, then PostgreSQL if the catalog grows

## Suggested database schema

### `parts`

| column | type | purpose |
| --- | --- | --- |
| `id` | integer | internal id |
| `part_number` | text | Nissan part number |
| `description` | text | part description |
| `supplier_url` | text | external source link |
| `part_family` | text | groups equivalent parts |

### `diagrams`

| column | type | purpose |
| --- | --- | --- |
| `id` | integer | internal id |
| `name` | text | diagram title |
| `image_path` | text | diagram file |
| `system_name` | text | engine, brake, cooling, etc. |

### `diagram_hotspots`

| column | type | purpose |
| --- | --- | --- |
| `id` | integer | internal id |
| `diagram_id` | integer | linked diagram |
| `callout_number` | text | number printed on the diagram |
| `part_number` | text | linked Nissan part number |
| `x_percent` | real | horizontal position |
| `y_percent` | real | vertical position |

## What the importer already does

- Reads the `Organized Parts` sheet into part records.
- Reads the `Sources` sheet into approved supplier domains.
- Reads `Sheet1` and attaches available supplier links to matching part numbers.
- Reads the `diagrams` sheet into diagram records.
- Extracts embedded diagram images from the workbook into `assets/diagrams`.
- Groups similar parts by matching normalized description text.

## How your website link fits in

You mentioned that every part should have a hyperlink from a website you know. The safest approach is:

1. Save the full URL in the `supplier_url` field.
2. Show that link in the side panel.
3. If the website URL follows a fixed pattern, generate it automatically instead of entering it manually.

Example generated URL rule:

```text
https://your-site.example/parts/{partNumber}
```

## Amayama-first workflow

For the latest GT-R R35 catalog, the cleaner workflow is:

1. Start from an Amayama catalog root such as:

```text
https://www.amayama.com/en/genuine-catalogs/epc/nissan-usa/gt-r/r35/614-vr38dett
```

2. Download each section page into the project:

```powershell
npm run scrape:amayama -- "https://www.amayama.com/en/genuine-catalogs/epc/nissan-usa/gt-r/r35/614-vr38dett"
```

This writes a local folder under `data/amayama-pages/` containing:

- `000-root.html`
- one saved HTML page per section
- `manifest.json`

3. Import the downloaded Amayama pages into the app data:

```powershell
npm run import:amayama -- data/amayama-pages/r35-614-vr38dett
```

Or import from the manifest directly:

```powershell
npm run import:amayama -- data/amayama-pages/r35-614-vr38dett/manifest.json
```

4. Rebuild hotspot and grouped catalog data if needed:

```powershell
npm run build
```

This is the preferred setup for your project because it naturally supports:

- multiple year/model versions of the same system
- multiple diagrams shown together in a vertical flow
- Amayama-style exploded diagram browsing
- local review of each saved section page one by one

The frontend already groups diagram variants into a single system family when possible, so one family page can show several stacked versions of the same diagram view.
